# 1. ROLE AND MISSION

Act as a senior mobile application engineer, product architect, UI/UX designer, AI integration engineer, database engineer, security specialist, and QA engineer.

Your task is to build **Plantly**, a polished, production-minded, cross-platform mobile application that helps people identify plants, understand possible plant-health problems, establish personalized care routines, and keep their plants healthy.

Plantly must not be a static prototype or a collection of attractive screens. Build a functioning application with real navigation, persistent data, authentication, image handling, backend integration, AI-assisted plant analysis, care scheduling, task completion, and a clear foundation for subscriptions.

The application must balance four priorities:

1. Premium design and a coherent brand identity.
2. Reliable plant-care functionality.
3. Affordable implementation and operating costs.
4. An architecture that can evolve beyond the MVP.

Work incrementally. Inspect the existing repository before making changes, establish a plan, implement one coherent feature at a time, and verify each stage before continuing.

Do not stop after generating a plan or presenting sample code. Continue through the implementation stages that the available environment supports. Never claim that a feature is operational unless it has been implemented and verified.

Do not deploy publicly, purchase services, or create paid subscriptions without explicit authorization.

# 2. PRODUCT VISION

Plantly is an AI-powered plant-care companion for beginners, hobbyists, and experienced plant owners.

The central experience is simple:

1. A user photographs a plant.
2. Plantly attempts to identify it.
3. The user saves the plant to their personal collection.
4. Plantly helps assess visible symptoms when requested.
5. The application creates an editable care plan.
6. The user receives reminders, completes care tasks, and records observations.
7. The AI assistant explains care recommendations in accessible language.

The product should make plant care less intimidating. Users should understand not only what action to take, but why it may help.

**Brand promise:** Your plants, understood.

**Core principles:**
- Helpful rather than overwhelming.
- Evidence-aware rather than falsely certain.
- Personal rather than generic.
- Calm rather than gamified.
- Affordable to build and operate.
- Respectful of user privacy and plant-care uncertainty.

# 3. REQUIRED TECHNOLOGY STACK

Use the following default stack unless repository constraints or a documented technical blocker justify a change.

## Mobile application

- React Native.
- Expo with TypeScript.
- Expo Router for file-based navigation.
- React Native StyleSheet and a centralized design-token system.
- TanStack Query for server-state fetching, caching, and mutations where appropriate.
- React Hook Form and Zod for forms and validation when useful.
- Expo Image Picker or Expo Camera for image acquisition.
- Expo Notifications for local notifications and the foundation for push notifications.
- Expo SecureStore for small sensitive client-side values when needed.
- Expo Application Services (EAS) for managed builds and release preparation.

Prefer established Expo-compatible libraries. Do not introduce dependencies merely because they are fashionable.

## Backend and database

Use Supabase for:

- PostgreSQL database.
- Authentication.
- Private image storage.
- Row Level Security (RLS).
- Database migrations.
- Server-side functions for privileged operations.

Use Supabase Edge Functions or another appropriately secured server-side runtime for AI orchestration, external provider requests, subscription validation, and privileged business logic.

Do not expose service-role credentials or provider secrets in the mobile application.

## AI and plant identification

Implement provider-independent service interfaces for:

1. Plant identification.
2. Visual symptom analysis.
3. Personalized care recommendations.
4. Conversational plant-care assistance.

Select a suitable plant-identification provider only after confirming its current API, pricing, image requirements, licensing, and production terms.

Use a vision-capable AI model for symptom interpretation when suitable. Do not assume that a general vision model alone can reliably identify every plant or diagnose every disease.

Keep provider integrations behind server-side adapters so that services can be changed without rewriting the entire application.

If no provider credentials are available, implement the interface, validation, loading states, error handling, and clearly labeled development fixtures. Never represent fixture data as a real AI result.

## Subscription infrastructure

Prepare a subscription architecture compatible with Apple App Store and Google Play in-app purchases.

RevenueCat may be used to simplify cross-platform subscription management, subject to account setup, current SDK compatibility, and pricing review.

Subscription entitlements must be validated through a trusted integration. Do not grant premium access based solely on a client-side flag.

The app must remain testable without paid subscription infrastructure through a clearly identified development entitlement mode.

## Development environment

Preferred environment: Cursor with a local Git repository.

Alternative environments: Claude Code, Replit, or Google Antigravity.

The project must remain a conventional, portable codebase rather than depending on proprietary editor-only functionality.

## Layout rules

- Design around a reference width of approximately 393 points.
- Use a consistent 8-point spacing rhythm.
- Start with approximately 20-point horizontal screen margins.
- Plant cards: approximately 28-point corner radius.
- Bottom sheets: approximately 34-point top corner radius.
- Primary buttons: approximately 56-point height with pill-shaped corners.
- Interactive targets: at least 44 points where platform conventions permit.
- Use approximately 1.5-point outline icons for the intended visual style.
- Respect device safe areas, keyboard insets, and system navigation.
- Use generous whitespace and realistic plant photography.
- Apply glass effects selectively to floating navigation or camera controls, not every card.
- Avoid excessive gradients, neon effects, decorative dots, generic dashboards, and AI-generated visual clutter.

Support system appearance, a manual light/dark preference, and persistent theme selection.

# 9. SECURITY AND ROW LEVEL SECURITY

Enable RLS on every table containing user-specific data.

For user-owned records, enforce policies so users can read or modify only records they own.

For child records, verify ownership through the associated parent or explicit owner field. Do not rely on client-side filtering as an access-control mechanism.

Storage policies must restrict private plant images to authorized users.

Server-side functions must:

- Authenticate requests.
- Validate input schemas.
- Enforce request-size limits.
- Apply usage limits.
- Protect provider credentials.
- Return safe, structured errors.
- Avoid leaking secrets or internal stack traces.
- Verify ownership before accessing user data.

Use secure HTTPS communication and current supported dependencies.

Never include Supabase service-role keys, AI provider keys, or privileged subscription credentials in client bundles.

Use environment variables and provide a `.env.example` containing placeholder values only.

Implement account deletion and document how personal data and backups are handled.

# 10. AI SERVICE CONTRACTS

Create provider-independent service interfaces with validated request and response types.

## Plant identification

Input:

- Image or secure image reference.
- Optional user-provided context.

Output:

- Candidate common names.
- Scientific names where supported.

- Distinguishing observations.

## Symptom analysis

Input:

Output:

- Observed visual features.
- Possible explanations.
- Confidence or uncertainty.
- Additional information needed.
- Low-risk recommended checks.
- Escalation guidance when warranted.

## Care planning

Generate structured recommendations, not arbitrary application instructions.

Each recommendation should include:

- Task type.
- Reason.
- Suggested timing or interval.
- Relevant conditions.
- Confidence or evidence level.
- Whether user confirmation is required.

Validate model outputs before storing or applying them. Reject malformed dates, unsupported task types, unreasonable intervals, and missing required fields.

## Assistant

Use a server-side orchestration layer with constrained tool access.

Allow only explicit, validated operations such as reading a user's authorized plant details, retrieving care logs, or proposing a schedule change.

Require user confirmation before applying significant changes.

Do not execute arbitrary model-generated SQL, code, shell commands, or external requests.

8. `SECURITY.md`: secrets, RLS, storage policies, privacy, and account deletion.

Keep documentation aligned with actual code. Do not document an integration as complete when it remains a placeholder.

# 21. IMPLEMENTATION MILESTONES

Build in this order.

## Milestone 1: Foundation

- Inspect the repository.
- Set up or repair the Expo TypeScript project.
- Configure routing.
- Implement design tokens and light/dark themes.
- Add typography and base components.
- Create the main navigation shell.
- Build the initial welcome screen.
- Add linting, type checking, and baseline tests.

**Exit criteria:** The app starts, navigation works, and the theme system functions.

## Milestone 2: Backend and authentication

- Configure Supabase.
- Add migrations.
- Implement RLS and storage policies.
- Implement authentication.
- Add profile preferences.
- Connect the application to the backend.
- Document environment setup.

**Exit criteria:** Authenticated users can access only their own records.

## Milestone 3: Plant collection

- Build My Plants.
- Build manual plant creation.
- Implement plant detail screens.
- Implement image upload and management.
- Add edit, archive, and delete actions.
- Add empty and failure states.

**Exit criteria:** Plant records persist across sessions and respect ownership boundaries.

## Milestone 4: AI scanning

- Select and configure a plant-identification provider.
- Implement secure image upload and server-side requests.
- Add typed provider adapters.
- Build scan and results screens.
- Validate response schemas.
- Implement uncertainty and retry handling.
- Add a documented development fixture mode.

**Exit criteria:** A configured provider can process an actual image, and errors or uncertain results are handled honestly.

## Milestone 5: Care planner

- Implement care plans and tasks.
- Add care logs.
- Implement schedule editing and completion.
- Add local reminders.
- Connect care data to the Home dashboard.
- Test recurrence and timezone behavior.

**Exit criteria:** Users can manage care tasks and review their history.

## Milestone 6: AI assistant and symptom analysis

- Implement structured symptom-analysis requests.
- Implement the conversational assistant.
- Add authorized plant context.
- Apply usage limits.
- Add safeguards for uncertain recommendations.
- Add retry, error, and confirmation flows.

**Exit criteria:** AI features use real configured services or clearly labeled development fixtures, with validated outputs.

## Milestone 7: Freemium and launch readiness

- Implement entitlement abstraction.
- Add subscription UI and provider integration when configured.
- Add restore-purchase handling.
- Add usage reporting.
- Complete privacy and deletion flows.
- Finalize accessibility and performance checks.
- Run test suites and build validation.
- Complete release documentation.

**Exit criteria:** The app is ready for a controlled test release, with remaining external setup and known limitations documented.

# 22. ACCEPTANCE CRITERIA

The MVP is not complete until:

- The app launches successfully in its supported development environment.
- iOS and Android share the intended product experience.
- Light and dark themes work across all core screens.
- Navigation and core interactions are functional.
- Authentication works when configured.
- Plant data persists in the backend.
- RLS prevents unauthorized access to user data.
- Image uploads respect ownership and validation rules.
- Identification uses a real configured provider in production mode.
- AI analysis communicates uncertainty appropriately.
- Users can create, edit, complete, and review care tasks.
- Care history is not fabricated.
- Reminders respect user preferences and timezone.
- AI usage and failures are controlled.
- Subscription entitlements cannot be self-granted by the client.
- Loading, empty, permission-denied, and error states are implemented.
- Automated tests cover critical business logic and access boundaries.
- Required documentation and environment templates are present.
- No secrets are committed.
- Known limitations and external dependencies are documented.
- No test, build, or deployment is claimed successful without verification.

# 23. FINAL EXECUTION INSTRUCTIONS

Begin by inspecting the repository.

Then:

1. Summarize the existing project state.
2. Present the proposed implementation sequence and identify blockers.
3. Create or update the documentation and baseline project structure.
4. Implement the first milestone.
5. Run the relevant checks.
6. Fix errors introduced by the implementation.
7. Report what is genuinely complete, what has been tested, and what still needs configuration.
8. Continue milestone by milestone without silently substituting mock functionality for real functionality.

Prioritize working vertical slices over large amounts of disconnected code.

If a choice must be made between visual polish and essential reliability, maintain the approved visual identity while ensuring authentication, data ownership, core care flows, and AI error handling are sound.

Do not overbuild the MVP. Defer social networking, plant marketplaces, smart-home integrations, complex gamification, and unrelated features unless explicitly requested.

Do not make live external service calls, purchase plans, publish the application, or deploy production infrastructure without the required credentials and authorization.

**Final objective:** Deliver a polished, accessible, maintainable, cross-platform Plantly MVP that helps users understand their plants and take sensible care actions, with a clear path to sustainable AI usage and future growth.
